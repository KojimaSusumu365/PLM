# PLM-L1-SS-doc v0.3 実施報告

## 結論

「訂正対応のSS記憶保持と再照会時の意味保持生成」を実装・試験した。外部で確認した役割と値の対応をSS係数へ学習し、保存・再読込した記憶から、新しい未確定観測の対象項目を補い、二／三事象の短文書を生成できた。

背景教師を512回提示した条件で、保護付き記憶は96照会中95件を正しく完成し、1件を保留、誤完成は0件だった。各照会に二つの出力方針を要求し、意味の正しい生成文書は190/192件だった。同じ学習係数容量を全て共有記憶に使う方式は60/96件、正しい生成120/192件だった。

ただし、保護付きの結合型とラベル別型は同成績である。「保護領域を設けた構成がこの干渉条件で有効だった」とはいえるが、結合型SSだけの優位性や、一般的な言語能力の向上を示したものではない。`eligible_for_inference=false`。

## 何を新しく学べるようになったか

v0.2は、その場の未確定な意味信号を外部情報で訂正する。v0.3ではその対応を長期側のSS係数へ学習し、後日の再照会に利用する。保存するのは訂正済みパケットや完成文ではない。

学習対象は「この出来事の、この項目で以前確認された値」。既存の文法・語彙・生成係数は変更していない。SS-activeの共有誤差・保護記憶という考え方を文書課題に別実装したもので、旧SS-active全体やP1/S1の統合ではない。

## 実際の生成例

同梱デモは、第二事象の主体だけが異なる次の二つの読みを明示的に与える。

> 太郎が花子を助けた。その後、花子が健太を褒めた。その後、健太が美咲を訪ねた。
>
> 太郎が花子を助けた。その後、由紀が健太を褒めた。その後、健太が美咲を訪ねた。

「第二事象の主体は由紀」と外部確認し、SS記憶へ学習する。別IDの背景教師12件を学習した後、記憶を保存・再読込する。再照会には、第二事象の主体の値を抜いた新しい未観測パケットを渡す。

出力順を反転した実際の生成結果：

> 健太が美咲を訪ねた。その前に、由紀が健太を褒めた。その前に、太郎が花子を助けた。

由紀をSS記憶から補い、他の主体・対象・行為と時間関係を保持して生成した。学習前と別episode IDへの照会は保留された。これは説明用デモで、主評価の独立標本には加えていない。二つの読みを自動発見する実証でもない。

証拠：[デモ全記録](examples/run/EXAMPLE.json)、[未観測の入力パケット](examples/run/fresh-packet.json)、[実際のCLI出力](verification/CLI.json)。実行方法は[README](README.md)を参照。

## 仕組みと通常処理との境界

外部指定のepisode ID、対象の事象と役割、事象数、提示順、対象以外の意味からキーを作る。対象の値・状態・候補集合はキーに含めない。そのため、以前の二候補を新しい未観測や読み取り不能の照会へ再利用できる。ただし、対象外の意味やIDが変われば別キーになる。

4本の複素位相符号で文脈と役割／値ラベルを表し、外部教師と4本の平均読み出しとの差を全チャネルへ共有更新する。結合型は文脈符号とラベル符号の積を重畳する。ラベル別型はラベルごとの係数に文脈符号を重畳する。数式と受理規則は[仕様書](SPECIFICATION.md)に記載した。

通常の登録台帳はキーのハッシュ集合と更新回数を持つが、キーから教師値を引く表は持たない。固定の23候補語彙は通常メタデータにも存在する。Python制御、ハッシュ、登録ゲート、外部ID、保護指定も使用するため、全処理をSS化したとはいわない。推論で取り出した予測を教師として自己学習しない。

保護記憶は、外部で保護指定した訂正教師だけを学習する。背景教師は共有記憶だけを更新する。保護対象や受理規則そのものを学習で発見したのではない。

## 固定した主評価

開発用8訂正＋32背景事例で32件の再照会を確認した後、ソース・モデル・データ・設定を凍結した。評価結果を見て閾値や符号次元を変更していない。凍結はローカルの再現性管理であり、外部機関への事前登録ではない。

- 2データ集合。それぞれ訂正対象24件（二事象12件、三事象12件）と背景256件。
- データ集合間と開発用集合の意味場面は非重複。評価には合計48訂正事例、512背景事例を用いる。
- 2符号seed、背景負荷2水準、比較5方式で40条件。
- 各条件で訂正教師24件を一度ずつ学習。その後、背景64件または256件を二巡、すなわち128回または512回提示。
- 記憶を実際に保存・再読込してから、各条件24件の新しい照会を行う。未確定状態は二候補・未観測・読み取り不能を順に割り当てる。
- 生成は提示順維持／主体先行と、順序反転／対象先行と主体先行の交互指定の二方針。

主評価は960照会、1920生成要求。同じ48訂正場面を方式・符号・負荷で繰り返す対応付き比較であり、960種類の独立した自然文書ではない。評価用の再照会は既知の制御意味から作った観測を符号化する。任意の自然文の曖昧性や出来事同一性を発見する試験ではない。

対象役割は主体・対象・行為・肯否・仮定・隣接事象の時間関係を含むが、全語彙×全役割×全位置の網羅ではない。自由な長文や未知語は対象外。生成文は、生成器とは別の制御文法採点器で意味・時間関係・出力方針を採点し、既存読解器による再読解も確認した。これは人間による自然さの評価ではない。

計画：[PROTOCOL.json](evaluation/PROTOCOL.json)、[データ監査](verification/DATA_AUDIT.json)。

## 主評価結果

各行の分母は96照会、192生成要求。保留された照会は文書を出さない。「記憶なし」の0件は、この未確定項目を追加確認なしでは補えないという意味で、既知の完全な意味から生成できないという意味ではない。

### 背景64件を二巡：128回提示

| 方式 | 正しい完成/96 | 誤完成 | 保留 | 正しい生成/192 | 誤生成 |
|---|---:|---:|---:|---:|---:|
| none | 0 | 0 | 96 | 0 | 0 |
| shared736 | 93 | 0 | 3 | 186 | 0 |
| shared1472 | 96 | 0 | 0 | 192 | 0 |
| split_pair | 96 | 0 | 0 | 192 | 0 |
| split_bank | 96 | 0 | 0 | 192 | 0 |

### 背景256件を二巡：512回提示

| 方式 | 正しい完成/96 | 誤完成 | 保留 | 正しい生成/192 | 誤生成 |
|---|---:|---:|---:|---:|---:|
| none | 0 | 0 | 96 | 0 | 0 |
| shared736 | 13 | 1 | 82 | 26 | 2 |
| shared1472 | 60 | 0 | 36 | 120 | 0 |
| split_pair | 95 | 0 | 1 | 190 | 0 |
| split_bank | 95 | 0 | 1 | 190 | 0 |

shared736の学習係数は47,104 bytes。他のSS三方式は94,208 bytesで一致する。固定基底・通常メタデータ・演算時間・全RAMまで同じではない。保護領域へ背景を入れない割当てを含む構成比較であり、万能なSS方式の優位性を結論しない。

訂正24件の学習直後は、SS四方式とも全対象を正しく支持した。背景学習後に差が生じた。主評価で補完した全ケースの対象外意味変更は0件。正しい生成件数は再読解で意味が一致した件数とも一致した。ただし対象そのものの誤りはshared736に1件あり、「意味を壊す生成が全方式で0」とはしない。

全数値：[SUMMARY.json](verification/SUMMARY.json)、[条件一覧](results/INDEX.json)、[全条件の生成・相関・採点](results/conditions)。

## 失敗例をどう解釈するか

高負荷の `d100-c1-b256-shared736`、`d100/1` では、正解の主体「太郎」に対して共有記憶が「健太」を支持した。未観測だった主体を誤補完し、二方針とも誤った文書を生成した。

同じ照会でsplit_pairとsplit_bankの保護記憶は「太郎」を正しく支持したが、共有側が「健太」を強く支持したため、`memory_disagreement` として保留した。保護記憶単体の支持は高負荷でも各方式96/96正しかった。しかし最終的に安全に完成できた件数は95/96であり、両者を混同しない。保護係数が背景学習で変わらないことも検査した。

この保留を無条件で保護側優先に変えれば、今回の点数は上がる可能性がある。しかし保護側の情報が古い／誤っている場合への対処とは別問題なので、本版では結果を見た規則変更をしていない。詳細：[AUDIT.json](verification/AUDIT.json)。

## 混同、明示情報、再訂正の試験

各方式・負荷について、同文別ID96件と、同IDで対象外の意味を変えた96件を照会した。全方式で最終補完は0件だった。

ただし、台帳の手前の生SS支持は高負荷で誤受理を示した。shared736は別ID2件／文脈変更2件、shared1472は0件／1件。split_pairとsplit_bankも共有側で2件／2件、保護側では0件／0件だった。従って、最終誤適用0を「SSだけで未登録を判別した」と解釈しない。ラベルなし登録ゲートが必要な構成である。

明示的な矛盾は各方式・負荷24/24件で保留した。新しい明示値を古い値で上書きしたケースも0件。ただし弱い記憶しかなければ新しい明示値をそのまま使うので、「新しい値には必ず再確認する」という規則ではない。高負荷の保護付き二方式では24件中23件を再確認待ちとし、1件は新しい値を保持して進んだ。

別の記憶分岐で最初の6件に明示的な改訂教師を与えると、SS四方式とも各方式・負荷24/24件の再照会を新しい値で正しく完成・生成した。これは主評価とは別の再訂正試験であり、同じ事例の反復を新しい独立標本として加算しない。

### 再訂正が他の保持項目へ与える影響：補足監査

主評価後の追加監査として、6件の再訂正後に残り18件を照会した。40条件×18件＝720件で、ここは意味補完だけの検査であり、全文書生成の追加評価ではない。

| 背景提示回数 | 方式 | 再訂正前の正しい補完/72 | 再訂正後の正しい補完/72 | 再訂正後の誤補完 |
|---|---|---:|---:|---:|
| 128 | none | 0 | 0 | 0 |
| 128 | shared736 | 70 | 69 | 0 |
| 128 | shared1472 | 72 | 72 | 0 |
| 128 | split_pair | 72 | 72 | 0 |
| 128 | split_bank | 72 | 72 | 0 |
| 512 | none | 0 | 0 | 0 |
| 512 | shared736 | 13 | 11 | 0 |
| 512 | shared1472 | 43 | 42 | 0 |
| 512 | split_pair | 72 | 72 | 0 |
| 512 | split_bank | 72 | 72 | 0 |

共有記憶では再訂正が他の照会の受理にも影響する。高負荷shared1472の合計43→42は、元の正解4件の保留化と、それまで保留だった3件の正解化の差である。保護方式の72→72は今回の範囲での保持であり、任意回数の改訂に対する保証ではない。[補足の全結果](verification/REVISION_COLLATERAL.json)。

## 保持は真実性の保証ではない

入力と記憶を一切変えず、評価器だけの正解値を別の値へ変更する対照も行った。高負荷の保護付き二方式は24件中23件で以前の値を保持し、1件を保留した。新しい評価値を正しく出した件数は0件だった。

これは、観測されていない変化をモデルが知ることはできないという境界を示す合成対照であり、現実世界の変化検出試験ではない。誤った外部教師も真偽を判定せず学習することを単体試験で確認した。「覚えている」「相関が強い」と「今も正しい」は別である。能動的な教師選択や、実際の再確認回数を最適化する閉ループは未実装。

## 検証・費用・旧版保全

32単体試験が成功した。制御文法の既存完全文回帰は144/144件成功した。全評価を二回実行し、処理時間の記録を除く207結果ファイルがバイト単位で一致した。80保存記憶状態を読み込み、各条件の先頭2件、合計80件の新しい再照会を再計算し、保存された全66基準信号も一致した。

別プロセスの隔離生成では、現在の教師データ・reader・新しい長期学習器・評価器を置かず、未観測の数値パケット、記憶、既存言語モデルから二事象・三事象の2件を生成できた。既存の局所数値更新器は必要である。「過去の教師由来情報までない」「全ての更新用コードがない」という意味ではない。

三事象デモの再照会＋生成時間は、1回のウォームアップ後7回の中央値で約0.099秒。この値はモデル読込や外部教師待ちを含まず、専有ホストでの性能比較でもない。デモの保持係数94,208 bytesに加え、固定ラベル基底2,166,784 bytes、実行後キャッシュ94,208 bytes、通常メタデータ2,197 bytesがある。既存部分文書基底33,947,648 bytesと生成文書基底10,747,904 bytesも別途必要。これらの部分計測を総RAMや省電力性の証明にしない。[費用記録](verification/BENCHMARK.json)。

旧v0.2の185ファイルと旧ZIPは不変。継承したPythonソース34ファイルと既存言語モデルを変更していない。推論前後の保存比較でも言語モデルとSS保持係数は不変だった。[保全検証](verification/PRESERVATION.json)。環境はPython 3.12.14、NumPy 2.3.5、Windows 11。

## 今回の到達点

限定された二／三事象について、外部確認した対応をSSに保持し、再読込後の新しい未確定観測から意味を保って書く接続実証ができた。次に解くべき課題は、古い確認と新しい確認の扱い、保護領域の容量制約・選択、そして外部IDに頼る同一出来事照合の境界である。本版では自動同一性判断、複数未確定項目の依存推論、未知語、自由長文、P1/S1接続までは進めていない。
